# 登录验证码 · 需求说明

> 基线文档：背景、决策、落地结论与验证记录。

## 一、背景与问题

登录接口 `/auth/login` 原本只需账号+密码，无任何防机器人/防爆破手段。老师要求登录时加验证，并希望优先使用现成开源组件（滑动/选择/图形等），先出方案再落地。

## 二、目标与非目标

**目标**
- 登录具备基础的机器人/暴力尝试拦截能力。
- 老师本人日常登录**零打扰**。
- PC 端 `/login` 与手机遥控页 `/m`（共用 `/auth/login`）同时生效。

**非目标（本期不做）**
- 不做滑块/点选等行为验证码，不引 Redis，不做账号锁定/限流。
- 不改 JWT/密码策略，不给其他敏感操作加验证码。

## 三、已确认决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | 用 easy-captcha **字符图形验证码**（4 位，SpecCaptcha 130×48） | 纯 Java AWT、无中间件、SB3/JDK17 兼容；手机端输 4 个字符即可，滑块在小屏体验差 |
| 2 | **连续失败 3 次后才出现**验证码，成功登录清零 | 平时无感，仅反复试密码时拦截 |
| 3 | 计数与验证码均存**内存**（ConcurrentHashMap），不落库不引 Redis | 内网单机部署，重启清零可接受；与项目既有内存态模式一致 |

**方案变更记录**：原计划用算术验证码（ArithmeticCaptcha，如 `3+5=?`），实测其依赖 Nashorn 脚本引擎求值，该引擎自 JDK15 起移除，JDK17 下 `ScriptEngine` 为 null 直接报错；改用字符图形码 SpecCaptcha，功能等价。

## 四、需求范围 / 影响范围

**后端**
- `pom.xml`：引入 `com.github.whvcse:easy-captcha:1.6.2`。
- 新增 `auth/CaptchaService.java`：
  - 失败计数：key = `账号(小写)|IP`，窗口 30 分钟，阈值 3 次；`onFail/onSuccess/needCaptcha`。
  - 验证码存储：captchaId → {答案, 过期时间}，TTL 5 分钟，**一次性**（验完即删，防复用）；发码时懒清理过期项。
- `auth/AuthController.java`：
  - 新增 `GET /api/auth/captcha`（公开）→ `{captchaId, img(data URI)}`。
  - `POST /api/auth/login`：达阈值先验验证码（缺失→"请完成验证码"，错误→"验证码错误"，均不查库不计失败）；账号不存在/密码错误时计数 +1，响应 data 带 `needCaptcha=true`（第 3 次失败起）；成功清零。
  - IP 取 `X-Forwarded-For` 首段 → `X-Real-IP` → `remoteAddr`。
- `config/WebConfig.java`：拦截器放行 `/api/auth/captcha`。
- `common/Result.java`：补 `fail(code, msg, data)` 静态方法。

**前端（PC + 手机共用接口，两处 UI）**
- `api/http.js`：业务失败 reject 的 Error 挂 `code/data`，调用方可读 `needCaptcha`。
- `views/Login.vue`：失败达阈值后密码框下出现验证码行（点图换一张 + 输入框，回车提交）；登录请求带 `captchaId/captchaCode`。
- `views/Mobile.vue`：`/m` 登录卡同款紧凑验证码行（原生 input + 缩略图），`doLogin` 补 try/catch 处理。

## 五、验收标准

- 连错 2 次无验证码；第 3 次失败起登录页出现验证码图。
- 验证码图可点击刷新；不带/带错验证码均被拒并提示；同一验证码用第二次无效。
- 验证码正确 + 密码正确 → 登录成功，失败计数清零，之后正常登录不再要验证码。
- PC `/login` 与手机 `/m` 行为一致。

## 七、安全说明

阈值验证码是机器人/暴力尝试的**拦截与减速手段**，非强安全防线（图形码可被 OCR）。内网单租户部署下与 BCrypt 密码哈希配合足够；后续若暴露公网，应再加账号锁定/限流或滑块行为验证。
